# راهنمای رفع اشکال یکپارچه‌سازی Sadr Scales

این صفحه برای مسیر پایه **Sadr Scales 5.2.1 / SQL Contract v1 / SDK 1.x** است.

## از اینجا شروع کنید

پیش از بررسی کد نرم‌افزار مقصد:

1. مطمئن شوید Sadr Scales 5.2.1 یا نسخه سازگار با Contract v1 اجرا شده و بررسی/به‌روزرسانی ساختار بانک اطلاعاتی آن کامل شده است.
2. روی همان بانک `await client.ValidateAsync()` یا فایل `samples/SQL/00-validate-contract.sql` را اجرا کنید.
3. ابتدا با داده آزمایشی و غیرواقعی تست کنید.
4. Cursor فروش را در نرم‌افزار مقصد و در یک محل پایدار نگهداری کنید.

## خطای `SadrContractMismatchException`

بانکی که به آن وصل شده‌اید با ساختار فریز‌شده SQL Contract v1 سازگار نیست.

بررسی کنید:

- Connection String به بانک درست Sadr Scales اشاره کند؛
- خود Sadr Scales یک‌بار اجرا شده و بررسی/به‌روزرسانی Schema را انجام داده باشد؛
- بانک یک نسخه قدیمی، کپی ناقص یا Backup نیمه‌به‌روزشده نباشد؛
- تغییرات شخص ثالث ستون‌ها، کلیدها یا نوع داده‌های Contract v1 را عوض نکرده باشد.

برای عبور از این خطا، کنترل Contract را در SDK دور نزنید.

## خطای ورود SQL یا بازشدن Database

معمولاً از نام Server/Database/User اشتباه یا دسترسی ناکافی SQL است.

SDK Connection String را پنهانی تغییر نمی‌دهد و تنظیمات امنیتی SQL را هم برای راحتی ضعیف نمی‌کند. تنظیمات استقرار را اصلاح کنید و Credential واقعی را داخل Source Code قرار ندهید.

## خطای Certificate یا Encryption در SQL

برای محیط واقعی، TLS/Certificate مناسب SQL Server را تنظیم کنید. فقط برای رفع سریع خطا، Encryption را در محیط Production خاموش نکنید.

`TrustServerCertificate=True` می‌تواند در محیط توسعه کنترل‌شده کاربرد داشته باشد، ولی سیاست امنیت Production بر عهده Integrator و محیط مشتری است.

## Timeout یا قطع موقت ارتباط

Retry خودکار SDK عمداً فقط در مرزهای امن انجام می‌شود:

- بازکردن Connection پیش از شروع Command؛
- اجرای کامل و فقط‌خواندنی Contract validation؛
- اجرای کامل و فقط‌خواندنی Sales query.

Writeهای Transactional گروه و کالا پس از شروع اجرا **به‌صورت خودکار Replay نمی‌شوند**؛ چون اگر پاسخ گم شود ممکن است معلوم نباشد Transaction Commit شده یا نه.

در چنین خطایی ابتدا وضعیت واقعی بانک را مشخص کنید و بعد درباره Retry تصمیم بگیرید.

## ردشدن Batch کالا پیش از اتصال به SQL

`UpsertBatchAsync` کل درخواست را قبل از SQL بررسی می‌کند.

علت‌های رایج:

- بیشتر از 200 PLU در یک فراخوانی؛
- تکرار `PluNo` داخل همان Batch؛
- داده نامعتبر کالا.

برای انتقال بزرگ‌تر، نرم‌افزار مقصد باید داده را خودش به Batchهای حداکثر 200 PLU یکتـا تقسیم کند.

## نتیجه `Unchanged` برای Upsert کالا

اگر مقدارهای معنایی کالا با Row فعلی بانک یکسان باشند این نتیجه طبیعی است. SDK Update بی‌دلیل انجام نمی‌دهد و `rowversion` SQL را در No-op تغییر نمی‌دهد.

## فروش تکراری در نرم‌افزار مقصد

Idempotency را در مقصد نگه دارید. کلید پیشنهادی Contract v1 برای جلوگیری از تکرار:

`(DeviceNo, FID, SubID)`

ابتدا داده فروش را در مقصد با موفقیت ذخیره کنید و بعد Cursor پایدار را جلو ببرید.

## وجود فاصله در ID فروش‌ها

فاصله داشتن ID طبیعی است و نباید پیوسته‌بودن شماره‌ها را فرض کنید.

الگوی خواندن:

```sql
WHERE ID > @LastProcessedId
ORDER BY ID ASC
```

آخرین ID که با موفقیت در مقصد ثبت شده باید به‌عنوان Cursor نگهداری شود.

## فروش جدیدی برنمی‌گردد

بررسی کنید:

- مقدار Cursor مقصد؛
- اتصال به بانک درست Sadr Scales؛
- اینکه فروش واقعاً توسط Sadr Scales پذیرفته شده باشد؛
- دسترسی `SELECT` کاربر SQL به `dbo.SADR_Logs`.

برای مدیریت Cursor جدول `SADR_Logs` را Update/Delete نکنید.

## نیاز به پروتکل مستقیم ترازو دارید؟

پروتکل مستقیم PLUS، LSG، Aclas و سایر مدل‌ها جزو SDK عمومی نیست. نرم‌افزارهای بیرونی از طریق SQL Contract/SDK با Sadr Scales یکپارچه می‌شوند و ارتباط مستقیم با دستگاه در اختیار Runtime خود Sadr Scales باقی می‌ماند.

## اگر مشکل باقی ماند

در Issue گیت‌هاب این اطلاعات را بنویسید:

- نسخه Sadr Scales؛
- نسخه SDK؛
- نسخه .NET/Runtime؛
- نسخه SQL Server؛
- API عمومی‌ای که خطا داده؛
- نوع Exception، متن خطا و Stack Trace بدون اطلاعات حساس؛
- نتیجه `ValidateAsync()`.

Connection String، رمز، اطلاعات مشتری، Capture شبکه یا فایل‌های محرمانه را در Issue عمومی قرار ندهید.
