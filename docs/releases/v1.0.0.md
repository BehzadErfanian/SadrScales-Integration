# SadrScales.Integration v1.0.0

First stable release of the official public C# integration SDK for **Sadr Scales SQL Contract v1**.

**Provided and maintained by Tozin Sadr and Behzad Erfanian.**

## Supported baseline

- Sadr Scales: **5.2.1** or later release explicitly documented as SQL Contract v1 compatible.
- SDK target: `netstandard2.0`.
- Proven consumer compatibility: .NET Framework 4.8 package consumer and modern .NET.
- SQL validation/integration gate: SQL Server 2022 with synthetic Contract v1 schema/data.
- License: MIT.

## Included SDK capabilities

- validate the expected SQL Contract v1 schema;
- create/update item groups;
- semantic PLU upsert without unnecessary rowversion changes;
- atomic bounded PLU batch upsert, maximum 200 unique PLUs per call;
- read accepted sales incrementally through a read-only API;
- destination-owned durable sales cursor;
- bounded retry for safe connection/read-only boundaries;
- explicit non-replay of transaction-scoped writes after execution begins.

## Important integration rules

- `PluNo` is the public Contract v1 PLU identity.
- Do not write SQL `rowversion`.
- Basic sales integration is read-only; do not update/delete `SADR_Logs` for acknowledgement/cursor management.
- Persist destination sales first, then advance the destination-owned cursor.
- `(DeviceNo, FID, SubID)` is the preferred destination duplicate-protection key.
- Source sales IDs may contain gaps.
- Larger PLU imports must be caller-paged into batches of at most 200 unique PLUs.

## Production readiness

Before enabling a customer integration, complete `docs/PRODUCTION_READINESS_CHECKLIST.md`. In particular, verify Contract compatibility, dedicated database access, destination-side cursor durability/idempotency, restart behavior and atomic-batch rollback.

## Security / scope boundary

This public SDK does **not** expose or implement direct PLUS/LSG/Aclas/device wire protocols, packet captures, firmware, private keys, customer data or internal Sadr Scales runtime source.

The caller owns SQL Server credentials and deployment security configuration. Never publish real connection strings or customer data in source code or public issues. Security-sensitive reports must follow `SECURITY.md`.
